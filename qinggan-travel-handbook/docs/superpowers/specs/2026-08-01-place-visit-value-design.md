# 地点游览价值层增量设计

## 目标

在不改变现有路由、地图能力、地点总数和整体视觉语言的前提下，让首页、地图地点卡片、地点列表与地点详情能够优先回答“为什么值得在这里停留”，并让时间有限的使用者快速完成取舍。

## 已确定的设计

### 数据结构

在 `Place` 中加入必填嵌套字段 `value: PlaceValue`。嵌套结构把判断性内容与已有玩法、拍照、预约和现场信息分开，后续修改文案时不会散落到多个字段。

```ts
export type PlacePriority = 'core' | 'recommended' | 'along-the-way' | 'interest' | 'optional'

export interface PlaceValue {
  reasonToVisit: string
  uniqueness: string
  bestFor: string[]
  priority: PlacePriority
  priorityLabel: string
  ifTimeIsLimited: string
  contrastWithNearby?: string
}
```

保留原有 `summary`、`recommendation`、`worthDetour` 等字段以兼容现有内容与组件，但四个本轮入口优先读取 `value`。16 个地点按真实取舍分布到五档，不把所有地点写成核心项目。

### 首页

在首页主视觉之后、路线索引之前增加“为什么是青甘大环线”。正文使用用户给定文案，下面是三个横向篇章卡片：文明向西、进入荒野、回到湖泊。卡片只承担路线叙事，不增加新的导航、日程或状态。

### 地图地点卡片

地图选中地点后，首屏顺序为名称、`reasonToVisit`、`priorityLabel`、建议停留时间、完整攻略入口与已去切换。图片保留为辅助视觉，但移到核心判断之后，避免在小屏底部卡片中挤占首屏。

### 地点列表

保留已有地貌分类筛选，增加独立的推荐等级筛选行。两组筛选取交集，状态继续写入 URL query，便于刷新后保留当前视图。地点卡片显示游览价值、等级、最多三项适合标签与已去状态。

### 地点详情

标题区后增加独立的价值总览组件，依次呈现：为什么值得去、最特别之处、推荐等级、适合谁、时间紧时如何选择；可选的附近对比仅在有内容时显示。原有常规玩法、非常规玩法、拍照、穿搭、预约、天气、健康安全、顺路组合全部保留，已去按钮只在页面末尾作为收束操作，避免它抢在判断信息之前。

## 方案取舍

- 采用嵌套 `value`，不把六个判断字段平铺进 `Place`：数据归属更清楚，组件接口也更稳定。
- 采用“类别 × 推荐等级”双筛选，不做互相替换的两套标签页：旅行中常见判断是“湖泊里哪些优先”，交叉筛选更有用。
- 新建轻量 `PlaceValueOverview`，不把价值模块塞进现有 `PlaceFacts`：前者负责取舍，后者继续负责停留、天气和步行等事实，两种信息不混在一起。

## 文案边界

- `reasonToVisit` 为 50 至 100 个汉字，说明景观、历史或路线叙事中的具体价值。
- 不使用“景色优美、值得打卡、不容错过、令人流连忘返、网红必去”。
- 语气理性、具体、允许舍弃；不出现固定 Day 行程、内部用户画像或命令式措辞。
- 不新增远程接口，不改变 localStorage、天气、高德地图和降级地图行为。

## 验收

- 16 个地点都通过类型与内容测试，拥有有效 `PlaceValue`。
- 首页、地图卡片、列表、详情四处都能看到价值判断。
- 分类与推荐等级筛选可组合，未知筛选值自动回到全部。
- 原预约、拍照、安全、天气、顺路组合和已去状态仍可使用。
- 390、820、1440 三种宽度无横向溢出，测试、类型检查与生产构建通过。
